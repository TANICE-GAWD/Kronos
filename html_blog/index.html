    Turning My OnePlus Nord Buds 3 Into a Wireless Mouse

    How I reverse engineered the tap sensors on my earbuds to control my laptop >> no app, no SDK, just Wireshark and stubbornness.

    Reading Time: 15 min
    Published: April 7, 2026
    Bluetooth Reverse Engineering Linux Go Wireshark

    Part 1 >> The Broken Phone

    My phone took a fall from the desk. The screen shattered across one corner>> not completely broken, but ugly enough to be annoying. I could've gotten it fixed, but instead I had an idea: I'd refuse to repair it until I finished the Poltergeist ear buds project. Broken phone equals constant motivation. Every time I reached for it, that cracked screen stared back at me>> a physical debt demanding payback.

    So I grabbed my Nord Buds 3 and started hacking. Wireshark, syscalls, reverse engineering. Three weeks later, I had a wireless mouse. And yeah, the phone's still broken. Worth it.

    Part 2 >> How Bluetooth Actually Works (The Part I Had to Learn)

    Before I could intercept anything, I needed to understand what I was looking at. Bluetooth is not one protocol >> it's two completely different stacks sharing the same radio.

    Classic Bluetooth (BR/EDR) is the old one. It handles audio (A2DP), phone calls (HFP), media controls (AVRCP), and serial port emulation (RFCOMM/SPP). This is what your earbuds use to play music.

    Bluetooth Low Energy (BLE) is the newer, power-efficient one. Devices expose a hierarchy of services and characteristics identified by UUIDs. You read, write, or subscribe to notifications on individual characteristics. This is what fitness trackers, smart bulbs, and IoT devices mostly use.

    I assumed the Nord Buds used BLE for everything >> because BLE is modern, BLE is what you'd choose if you were building something in the last decade, and BLE has a clean API for exactly this kind of event-driven notification. That assumption cost me two weeks.

    HCI Snoop Logs

    Android has a developer option called "Enable Bluetooth HCI snoop log." When turned on, every single Bluetooth packet going in or out of the phone gets written to a file. You pull it with adb, open it in Wireshark, and you can see exactly what any app sends to any device >> byte by byte. This turned out to be the most important tool I had. The packets don't lie.

    Part 3 >> First Attempt: BLE Notifications

    My first approach was simple. Enumerate all GATT services and characteristics, subscribe to every notifiable characteristic I could find, perform the device handshake, then tap the buds and watch for packets.

    I wrote a Go tool using tinygo.org/x/bluetooth. Service discovery gave me six services across two dozen characteristics. I subscribed to all of them:

    [SERVICE] 0000fe2c-0000-1000-8000-00805f9b34fb
  [CHAR] fe2c1234-8366-4814-8eb0-01de32100bea  -> subscribed
  [CHAR] fe2c1235-8366-4814-8eb0-01de32100bea  -> subscribed
[SERVICE] 0000079a-d102-11e1-9b23-00025b00a5a5
  [CHAR] 0200079a-d102-11e1-9b23-00025b00a5a5  -> subscribed
[INFO] Subscribed to 7 notification sources
[READY] Perform gestures now...

    I tapped every gesture the buds support. Double tap, triple tap, long press on each side.

    Nothing. Complete silence across all seven notification channels.

    I sent probe packets to try waking up whatever subsystem handled gestures. Tried every category byte from 0x01 to 0x10. No responses. The device was happily processing ANC commands but gesture events simply weren't arriving anywhere over BLE.

    Part 4 >> The Wireshark Revelation

    Something was clearly happening that I wasn't seeing. The HeyMelody app on Android receives tap events in real time >> I could watch the UI update when I tapped. That data had to be coming from somewhere.

    I enabled HCI snoop logging on my Android phone, opened HeyMelody, performed a tap, pulled the log, and opened it in Wireshark.

    Filtering for btatt (Bluetooth Attribute Protocol >> the BLE layer) gave almost nothing useful. Wireshark kept throwing "Frame is out of any connection handle session" errors on the few packets it did show.

    Then I tried filtering the raw data directly for the 0xAA start-of-frame byte that I knew all OPO packets begin with:

    data contains aa:07:00:00 || data contains aa:0c:00:00 || data contains aa:0a:00:00

    Fifteen packets matched. I clicked on one and looked at the protocol column.

    It said RFCOMM.

    Not ATT. Not BLE. Classic Bluetooth serial port protocol.

    I looked at the destination address. 9c:de:f0:33:f5:dd >> my Nord Buds MAC. The OPO packets >> the exact same 0xAA-prefixed format >> were travelling over a classic Bluetooth RFCOMM connection, not BLE GATT at all.

    That was why my BLE listener was completely silent. The gesture events were never on BLE to begin with. The two stacks coexist on the same device and serve completely separate channels. I had been looking in entirely the wrong place.

    Part 5 >> Finding the Channel

    RFCOMM connections use numbered channels. I needed to know which channel the buds exposed for the OPO control protocol.

    The standard way to discover this is SDP >> the Service Discovery Protocol, which acts like a registry of available services:

    sdptool browse 9C:DE:F0:33:F5:DD

    The OPO serial service wasn't registered at all. OnePlus intentionally omits it from SDP >> you can't discover it through normal means.

    But I had the Wireshark capture. Digging into the L2CAP layer of those RFCOMM packets revealed the channel number buried in the connection setup. I tried connecting directly:

    sudo rfcomm connect /dev/rfcomm0 9C:DE:F0:33:F5:DD 12
Connected /dev/rfcomm0 to 9C:DE:F0:33:F5:DD on channel 12

    Channel 12. Not 1, not 2, not any of the obvious guesses. The only way to find it was from the packet capture.

    Part 6 >> Rewriting for RFCOMM

    The entire BLE stack got deleted. tinygo.org/x/bluetooth, the adapter initialization, the service discovery loop >> gone. Replaced with about 30 lines of raw Linux syscalls.

    Go's standard library has no RFCOMM support. But the Linux kernel does, via AF_BLUETOOTH sockets with BTPROTO_RFCOMM. The connection struct mirrors the C header <bluetooth/rfcomm.h> exactly:

    type sockaddrRFCOMM struct {
    Family  uint16
    Dev     [6]byte  // MAC address, bytes reversed
    Channel uint8
    _       [1]byte  // padding
}

    The MAC address goes in reversed >> RFCOMM wants LSB first, opposite of how humans write MAC addresses. One connect syscall later, you have a plain bidirectional byte stream to the device. No characteristic handles, no notification subscriptions, no silent failures.

    First run after the rewrite:

    [OK] RFCOMM connected
[TX] HELLO: aa070000000123000012
[TX] REGISTER: aa0c000000854105000000b550a069
[RX RAW] aa0f000004020408000201030102030304...
[READY] Perform gestures now...

    Then I double-tapped the left bud.

    GESTURE: LEFT  DOUBLE TAP

    Three weeks of silence, and there it was.

    Part 7 >> Decoding the Gesture Packets

    I ran through every gesture the buds support and captured the raw bytes for all six combinations:

    GestureBud byteGesture byte
    Left double tap0x010x02
    Right double tap0x020x02
    Left triple tap0x010x03
    Right triple tap0x020x03
    Left long press0x010x04
    Right long press0x020x04

    The pattern is perfectly consistent. All gesture packets share CAT=0x04 SUB=0x02 with a 0xF1 marker at byte 9. After that: bud identity and gesture type, one byte each.

    Byte  4  = 0x04   CAT
Byte  5  = 0x02   SUB (gesture event)
Byte  9  = 0xF1   gesture marker
Byte 10  = BUD    0x01=Left  0x02=Right
Byte 11  = 0x01   constant
Byte 12  = TYPE   0x02=double  0x03=triple  0x04=long press

    Part 8 >> Mapping Gestures to Actions

    With the byte signatures identified, the last step was turning them into real system input. xdotool on Linux can synthesise mouse clicks, scroll events, and keypresses from the command line.

    GestureAction
    Left double tapLeft click
    Right double tapClick (link / button under cursor)
    Left triple tapScroll up ×5
    Right triple tapScroll down ×5
    Left long pressPlay / Pause
    Right long pressNext track

    Part 9 >> Full Implementation

    The complete tool. No external Bluetooth libraries >> just the Go standard library and Linux syscalls.

    package main

import (
    "encoding/hex"
    "fmt"
    "net"
    "os"
    "os/exec"
    "strings"
    "syscall"
    "time"
    "unsafe"
)

const (
    DEVICE_MAC     = "9C:DE:F0:33:F5:DD"
    RFCOMM_CHAN    = 12
    AF_BLUETOOTH   = 31
    BTPROTO_RFCOMM = 3
)

type sockaddrRFCOMM struct {
    Family  uint16
    Dev     [6]byte
    Channel uint8
    _       [1]byte
}

func parseMac(mac string) [6]byte {
    v, _ := net.ParseMAC(mac)
    var b [6]byte
    for i := 0; i < 6; i++ { b[i] = v[5-i] }
    return b
}

func connectRFCOMM() (int, error) {
    fd, err := syscall.Socket(AF_BLUETOOTH, syscall.SOCK_STREAM, BTPROTO_RFCOMM)
    if err != nil { return 0, fmt.Errorf("socket: %w", err) }
    addr := sockaddrRFCOMM{Family: AF_BLUETOOTH, Dev: parseMac(DEVICE_MAC), Channel: RFCOMM_CHAN}
    _, _, errno := syscall.Syscall(syscall.SYS_CONNECT, uintptr(fd), uintptr(unsafe.Pointer(&addr)), unsafe.Sizeof(addr))
    if errno != 0 { syscall.Close(fd); return 0, fmt.Errorf("connect: %w", errno) }
    return fd, nil
}

func hexStr(data []byte) string { return hex.EncodeToString(data) }

func sendRaw(fd int, data []byte, label string) {
    fmt.Printf("[TX] %s: %s\n", label, hexStr(data))
    syscall.Write(fd, data)
}

func doHandshake(fd int) {
    sendRaw(fd, []byte{0xAA,0x07,0x00,0x00,0x00,0x01,0x23,0x00,0x00,0x12}, "HELLO")
    time.Sleep(2 * time.Second)
    sendRaw(fd, []byte{0xAA,0x0C,0x00,0x00,0x00,0x85,0x41,0x05,0x00,0x00,0xB5,0x50,0xA0,0x69}, "REGISTER")
    time.Sleep(2 * time.Second)
}

func handleNotify(data []byte) {
    fmt.Println("[RX RAW]", hexStr(data))
    for i := 0; i < len(data)-12; i++ {
        if data[i] != 0xAA { continue }
        frameLen := int(data[i+1])
        if i+frameLen+2 > len(data) { break }
        cat, sub := data[i+4], data[i+5]
        if cat == 0x04 && sub == 0x02 && data[i+9] == 0xF1 {
            side := "LEFT"
            if data[i+10] == 0x02 { side = "RIGHT" }
            names := map[byte]string{0x02:"DOUBLE TAP",0x03:"TRIPLE TAP",0x04:"LONG PRESS"}
            gesture := data[i+12]
            name, ok := names[gesture]
            if !ok { name = fmt.Sprintf("UNKNOWN(0x%02X)", gesture) }
            fmt.Printf("\nGESTURE: %s %s\n", side, name)
            handleGesture(side, gesture)
        }
        if cat == 0x06 && sub == 0x81 && i+15 < len(data) {
            fmt.Printf("\n[BATTERY] L:%d%% R:%d%% C:%d%%\n", data[i+12], data[i+14], data[i+15])
        }
        i += frameLen + 3
    }
}

func handleGesture(side string, gesture byte) {
    switch {
    case side == "LEFT"  && gesture == 0x02: run("xdotool","click","1")
    case side == "RIGHT" && gesture == 0x02: run("xdotool","click","1")
    case side == "LEFT"  && gesture == 0x03: run("xdotool","click","--repeat","5","--delay","20","4")
    case side == "RIGHT" && gesture == 0x03: run("xdotool","click","--repeat","5","--delay","20","5")
    case side == "LEFT"  && gesture == 0x04: run("xdotool","key","XF86AudioPlay")
    case side == "RIGHT" && gesture == 0x04: run("xdotool","key","XF86AudioNext")
    }
}

func run(name string, args ...string) { exec.Command(name, args...).Run() }

func readLoop(fd int) {
    buf := make([]byte, 1024)
    for {
        n, err := syscall.Read(fd, buf)
        if err != nil { fmt.Println("[ERROR]", err); return }
        if n > 0 { handleNotify(buf[:n]) }
    }
}

func main() {
    if len(os.Args) < 2 { fmt.Println("Usage: go run main.go <listen|on|off|trans>"); return }
    fd, err := connectRFCOMM()
    if err != nil { fmt.Println("[ERROR]", err); return }
    defer syscall.Close(fd)
    go readLoop(fd)
    time.Sleep(300 * time.Millisecond)
    switch strings.ToLower(os.Args[1]) {
    case "listen":
        doHandshake(fd)
        fmt.Println("Nord Buds Gesture Remote READY")
        select {}
    case "on":    doHandshake(fd); sendRaw(fd, []byte{0xAA,0x0A,0x00,0x00,0x04,0x04,0x42,0x03,0x00,0x01,0x01,0x01}, "ANC ON")
    case "off":   doHandshake(fd); sendRaw(fd, []byte{0xAA,0x0A,0x00,0x00,0x04,0x04,0x42,0x03,0x00,0x01,0x01,0x04}, "ANC OFF")
    case "trans": doHandshake(fd); sendRaw(fd, []byte{0xAA,0x0A,0x00,0x00,0x04,0x04,0x42,0x03,0x00,0x01,0x01,0x02}, "TRANSPARENCY")
    }
}

    What I Learned

    The transport assumption kills you. I spent the first two weeks certain gestures were on BLE because that's what you'd choose if you were building this today. They weren't. Classic Bluetooth and BLE coexist on the same device, same MAC address, completely separate stacks. Never assume one maps to the other.

    The HCI snoop log is the fastest path to truth. Every hour spent guessing protocol details is an hour that could have been spent reading packets. Enable the log, perform the action, open Wireshark. The traffic shows you exactly what's happening in a way that no amount of guessing can match.

    RFCOMM is simpler than BLE once you find the channel. BLE GATT has services, characteristics, properties, write types that fail silently, notification subscriptions that do nothing. RFCOMM is a socket. Write bytes in, read bytes out. Every failure is loud and obvious.

    Channel 12 is not a number you'd guess. SDP was empty for the OPO service >> hidden intentionally. The only way to find it was from the snoop log. If you're doing this for a different OnePlus device, start there before anything else.
